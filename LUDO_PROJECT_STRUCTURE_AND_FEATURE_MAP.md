## 1. Project Overview

**LUDO** is the combined **marketing website + CMS + booking/payment system** for *LUDO Sports Kitchen & Coffee* (a sportsbar in Bandung, Indonesia). It is a single **Next.js 16 (App Router, Turbopack)** project — there is no separate backend service in this root. "Backend" logic lives inside the same codebase as:

- **Next.js Route Handlers** (`app/api/**/route.ts`) — for Midtrans payment/webhook, admin XLSX export, media upload, uploaded-file serving, and NextAuth.
- **Next.js Server Actions** (`server/actions/*.ts`, `"use server"`) — the primary CRUD backend for the entire CMS (events, matches, packages, tables, members, gallery, FAQ, brands, hero, location, settings, media).

### Stack

| Layer | Technology |
|---|---|
| Framework | Next.js (latest, App Router, Turbopack build) |
| Language | TypeScript |
| Styling | Tailwind CSS 3 |
| ORM / DB | Prisma 6 → **MySQL** (`newludo_db`) |
| Auth | NextAuth (Credentials provider, JWT session) + `proxy.ts` middleware guarding `/admin/*` |
| Payment | Midtrans Snap (sandbox/production toggle via env) |
| Validation | Zod |
| File export | `xlsx` (SheetJS) for admin transaction reports |
| Password hashing | `bcrypt` (admin users + Members) |
| Icons | `lucide-react` |
| Fonts | `next/font/google` (Bebas Neue, Montserrat) |

### What the system actually does

1. **Public marketing site** (`/`) — hero carousel, sports match schedule, events banner, location, FAQ, gallery, brand partners.
2. **Full booking + payment flow** — customers pick a table (or a seat, for community nobar events), pick a package, optionally add à-la-carte menu items, optionally apply a Member discount, and pay via Midtrans Snap.
3. **Delivery Order** — a singleton, always-available "order food/drinks" flow with categorized menu (Beverages/Food), reachable from the header nav, independent of any specific match/event.
4. **Admin CMS** (`/admin/*`) — content management for every public section, plus Members (discount codes), Matches (auto-provisions its own bookable event), Events, Transactions (per event, with Excel export).

## 3. Folder and File Explanation

### `app/` — routes, layouts, API handlers
Next.js App Router convention: every folder with a `page.tsx` is a public route, every `route.ts` is an API handler. `app/page.tsx` is unusually large (~700 lines) because it single-handedly aggregates **all** homepage sections and their fallback ("DEFAULT_*") demo data in case the database is empty or unreachable (see the `try/catch` in `getHomepageContent()`).
*Safe to edit*: yes, but `app/page.tsx`'s `DEFAULT_MATCHES`/`DEFAULT_EVENTS` arrays must be kept in sync with the `PublicMatch`/`PublicEvent` TypeScript types in `components/public/types.ts` (every field is required — a missing field breaks the build).

### `app/admin/` — CMS
Each subfolder is one CMS module. Almost all follow the same pattern: `page.tsx` (Server Component, `requireAdminSession()` + Prisma query) renders a form component from `components/admin/` whose `<form action={...}>` posts to a Server Action in `server/actions/`. **`app/admin/events/[id]/page.tsx`** is the most important admin page — it's where `PackageManager` and `TableManager` are rendered for a specific `BookingEvent` (unless its `eventType` is `REGULER_MATCH`, see §10).
*Safe to edit*: yes, but always keep the `requireAdminSession()` call at the top of every admin page/action — that's the only auth gate on top of `proxy.ts`.

### `app/api/midtrans/` — payment backend
`checkout/route.ts` is the most complex file in the project: it validates the package/table, verifies Member credentials (bcrypt), branches between **whole-table** and **per-seat (NOBAR_COMMUNITY)** locking, computes totals via `lib/pricing.ts`, creates the `Reservation` + `OrderItem`s, and requests a Midtrans Snap token. `webhook/route.ts` receives Midtrans's async payment notification, verifies the SHA-512 signature, and updates `Reservation.status` + `EventTable.status`/`bookedSeats`.
*Caution*: this is the highest-risk area in the app — see §19 Bug Risk Map before touching it.

### `app/book/[eventId]/` — public booking page
Dynamic route. Fetches one `BookingEvent` with its `packages` (active only) and `tables`. If `eventType === "REGULER_MATCH"` it renders a **WhatsApp-only CTA** instead of the booking form (see §10). Otherwise renders `<BookingForm>`.

### `app/delivery-order/` and the Delivery Order "singleton" pattern
There is exactly **one** `BookingEvent` row with `eventType = "DELIVERY_ORDER"` in the whole system, auto-created/fetched by `getOrCreateDeliveryOrder()` in `server/actions/deliveryOrderActions.ts`. Its `EventPackage` rows (with `category`/`subCategory` set) double as the global food/beverage menu — the same rows are reused as "à la carte add-ons" on other booking events when `BookingEvent.allowAlaCarte = true`.

### `components/admin/` — CMS UI
Reusable admin primitives: `AdminCard`, `AdminTable`, `AdminNotice`, `ConfirmSubmitButton` (modal confirm before destructive/important submits), `DeleteConfirmButton`, `FormFieldLabel`, `InfoTooltip`. Feature forms: `EventForm`, `MatchForm`, `PackageManager`, `TableManager`, `MemberForm`, `DeliveryOrderForm`, `HeroForm`, `GalleryForm`, `BrandForm`, `LocationForm`, `FAQForm`, `SettingsForm`, `MediaUploader`.
*Safe to edit*: yes. `PackageManager` and `TableManager` are shared between the generic Events CMS and the Delivery Order CMS (`mode` prop) — check both call sites before changing their prop shape.

### `components/public/` — public site UI
`Header`, `Footer`, `HeroSection`, `MatchSection` (sports schedule carousel), `EventBanner` (events carousel), `LocationSection`, `FAQSection`, `GallerySection`, `BrandSection`, `BookingForm` (the biggest client component — table/seat selection, package selection, à-la-carte cart, member login, price breakdown, checkout), `SeatMap` (renders the seat layout image + table buttons), `WhatsAppButton`, `EventMiceVenueLayout`.
*Caution*: `BookingForm.tsx` and `SeatMap.tsx` are tightly coupled to the Prisma `EventTable`/`EventPackage` shape — changing the schema without updating both will break the build.

### `lib/` — pure helpers (no DB writes except `upload.ts`/`prisma.ts`)
Notable: `lib/tableLayout.ts` is the **single canonical definition** of the LUDO table layout (VVIP/VIP/Regular/Barstool table codes, capacities, minimum-charge defaults) — used both by `eventTableActions.ts` ("Generate Tables" button) and `matchActions.ts` (auto-provisioning). `lib/pricing.ts` defines `ADMIN_FEE_RATE = 0.03` and `computeOrderTotals()` — used identically on the client (`BookingForm`, for display) and the server (`checkout/route.ts`, authoritative) so the numbers always match. `lib/bookingAvailability.ts` computes live BOOK/LIMITED/FULL_BOOKED + "X/Y tables left" from real `EventTable` rows.

### `server/actions/` — the CRUD backend
Every file is a `"use server"` module. Convention: `buildXData(formData)` (Zod-validated) → `createX`/`updateX`/`deleteX`/`toggleXActive`, each wrapped in `requireAdminSession()` and ending with `redirectWithMessage()` (success/error passed via query string, read by `<AdminNotice>`).
*Safe to edit*: yes, this is the intended extension point for new CMS features.

### `prisma/`
`schema.prisma` is authoritative. **Caution**: migration history (`prisma/migrations/`) is **out of sync** with the live schema — several models (`BookingEvent`, `EventPackage`, `EventTable`, `Reservation`, `OrderItem`, `Member`, etc.) exist in the database but have **no corresponding migration file**. They were applied via `prisma db push`, not `prisma migrate dev`. Running `prisma migrate dev` on this project **will prompt to reset the database** — never run it without first confirming with a human; use `prisma db push` instead. See §19.

### `public/uploads/`
Grows unbounded — every CMS image/video upload lands here with a `${timestamp}-${uuid}-${slug}.${ext}` filename (see `lib/upload.ts`). Served through the custom route `app/uploads/[...path]/route.ts` **in addition to** Next's normal static file serving of `public/` (both work; the custom route exists so uploaded files get long-lived cache headers).

### `proxy.ts` (Next.js Middleware)
Despite the filename, this is a standard Next.js `middleware.ts`-style file (exported as `proxy` + `config.matcher`). It redirects any unauthenticated request to `/admin/*` → `/admin/login`, and redirects an authenticated user away from `/admin/login` → `/admin`. This is the **only** route-level auth gate; every admin Server Action additionally calls `requireAdminSession()` as defense in depth.

## 7. Backend/API Structure

There is no standalone backend framework (no Express/Nest/Fastify, no `backend/` folder). The "backend" is:

1. **Next.js Route Handlers** (`app/api/**/route.ts`) — for payment, webhook, file upload/serving, export, and auth.
2. **Next.js Server Actions** (`server/actions/*.ts`) — for all CMS CRUD, invoked directly from `<form action={...}>` in Server/Client Components (no manual `fetch()` needed for CMS forms).
3. **Prisma Client** (`lib/prisma.ts`) — the only database access layer; there is no separate repository/service abstraction.
4. **Auth**: NextAuth Credentials provider (`lib/auth.ts`), JWT session strategy, `AdminUser` model with bcrypt password hash. `requireAdminSession()` is called at the top of every protected Server Action/admin page.
5. **File upload**: `lib/upload.ts` writes directly to `public/uploads/` on the local filesystem (no S3/cloud storage integration) — **this means uploads will not survive a stateless/serverless deployment** (e.g. Vercel) and require a persistent-disk host or a future migration to object storage.

### Relations

```text
BookingEvent (category: LIVE_EVENT | BOOKING_EVENT, eventType: EventTemplate)
 ├── has many EventPackage        (package/menu items; category+subCategory used for Delivery Order)
 ├── has many EventTable          (table/seat inventory; tableType, status, capacity, basePrice, bookedSeats)
 ├── has many Reservation
 └── has many MatchCard           (0..1 in practice — each match auto-provisions exactly one BookingEvent)

MatchCard
 └── belongs to BookingEvent (optional FK `bookingEventId`, onDelete: SetNull)
     — this is how "UPCOMING SPORTS SCHEDULE" gets a real payment flow

EventPackage
 ├── belongs to BookingEvent (onDelete: Cascade)
 └── has many OrderItem (onDelete: SetNull if package deleted)

EventTable
 ├── belongs to BookingEvent (onDelete: Cascade)
 └── has many OrderItem (onDelete: SetNull if table deleted)
 (@@unique on [bookingEventId, tableCode])

Reservation
 ├── belongs to BookingEvent (onDelete: Cascade)
 └── has many OrderItem (onDelete: Cascade)
     fields: status (ReservationStatus), totalPrice, tax (=admin fee), discountAmount,
             memberUsername, snapToken, transactionId (unique), paymentMethod,
             paymentCallbackData (raw Midtrans payload JSON), expiredAt

OrderItem
 ├── belongs to Reservation (onDelete: Cascade)
 ├── belongs to EventPackage (nullable)
 └── belongs to EventTable (nullable — null for à-la-carte add-on lines)

Member
 (standalone — username, passwordHash, discountPercent, benefitNote, isActive)
```

### Migration/schema caveat (important)

`prisma migrate status` reports **drift**: several tables that exist in the live MySQL database (`BookingEvent`, `EventPackage`, `EventTable`, `Reservation`, `OrderItem`, `Member`, `EventMiceSetting`, and the newer columns on `MatchCard`/`EventTable`) have **no corresponding file** in `prisma/migrations/`. They were applied directly with `prisma db push` during development. **Running `prisma migrate dev` will prompt to drop and recreate the database** — this happened once already this session and was aborted before any data loss. **Always use `prisma db push` for schema changes on this project unless someone deliberately reconciles the migration history first.**

## 10. Event Flow

Two parallel content types both end up as a **bookable `BookingEvent`**:

**A. Standalone Events** (admin-authored via `/admin/events`):
1. Admin picks Category (`LIVE_EVENT` = WhatsApp-only, or `BOOKING_EVENT` = full flow) and Template (`EventTemplate`).
2. `EventForm` → `eventActions.ts` (`createEvent`/`updateEvent`) → `BookingEvent` row created/updated.
3. If `BOOKING_EVENT` and template ≠ `REGULER_MATCH`, admin adds `EventTable`s (via "Generate Tables", using `lib/tableLayout.ts`) and `EventPackage`s (`PackageManager`).
4. Event appears on the homepage `EventBanner` (excluded if `eventType = DELIVERY_ORDER` **or** it has a linked `MatchCard`).
5. Customer clicks through to `/book/{id}`.

**B. Matches** (admin-authored via `/admin/matches`, "UPCOMING SPORTS SCHEDULE"):
1. Admin fills team names/league/date — **no manual event linking needed**.
2. `createMatch`/`updateMatch` in `matchActions.ts` **auto-provisions** a `BookingEvent` (`eventType: "BIG_MATCH"`, 48 tables generated from `lib/tableLayout.ts`) and sets `MatchCard.bookingEventId`.
3. Admin must separately add `EventPackage`s to that auto-provisioned event (via the "Manage packages →" link in the matches list) — **tables exist automatically, prices do not**.
4. Public `MatchSection` card shows a real "BOOK" button **only if** the linked event has ≥1 active package (`hasPackages`); otherwise it falls back to a WhatsApp button automatically (self-healing — no code change needed once packages are added).
5. Live status (BOOK/LIMITED/FULL_BOOKED) and "X/Y tables left" are computed from real table data via `lib/bookingAvailability.ts`, not stored/edited manually.

Status: **Existing** (both paths fully implemented this project cycle).

## 11. Package Flow

- Source of truth: **database** (`EventPackage` table), never hardcoded on the frontend. `PackageManager.tsx` is the only way to create/delete packages (no update — packages are delete+recreate in the current UI).
- Always tied to a `BookingEvent` via `bookingEventId` (required FK).
- `tableType` on a package determines which tables it's offered for (`BookingForm` filters `matchingPackages` by `pkg.tableType === selectedTable.tableType`).
- `category`/`subCategory` (Beverages/Food + subcategories from `lib/deliveryCategories.ts`) are **only meaningful for Delivery Order** packages, but the fields exist on every package row (nullable).
- **À la carte reuse**: when `BookingEvent.allowAlaCarte = true`, the booking page fetches the Delivery Order's own package list (`category: { not: null }`, `bookingEvent.eventType: "DELIVERY_ORDER"`) and offers them as optional add-ons on top of the table package — same underlying rows, no duplication.
- Directly used in booking/payment: yes — `checkout/route.ts` re-fetches the package server-side and uses its live `price`, never trusting client-submitted price.

Status: **Existing**, database-driven end to end.

## 12. Booking Table Flow

1. Customer opens `/book/{eventId}`.
2. Server Component fetches `BookingEvent` (must be `isActive`, category `BOOKING_EVENT`) with active `packages` and all `tables`.
3. If `eventType === "REGULER_MATCH"` → render WhatsApp-only CTA, **stop here** (no table/package UI at all).
4. Otherwise render `<BookingForm>`:
   - **Has tables** → Step 1: pick a table (`SeatMap`). Table buttons disabled unless `status === "AVAILABLE"`.
   - **NOBAR_COMMUNITY** → after picking a table, pick a **seat quantity** (see §13) instead of locking the whole table.
   - Step 2: pick a package (auto-selected if only one matches the table type — **except** for NOBAR_COMMUNITY, which always requires an explicit click, by design, so seats are chosen first).
   - Optional: à-la-carte add-ons, Member login (discount), customer details form.
   - Price breakdown (`lib/pricing.ts`): Total Belanja → (– Member discount, applied server-side only) → + Admin Fee (3%) → Grand Total.
5. On submit → `POST /api/midtrans/checkout`:
   - Whole-table events: `EventTable.status` flips `AVAILABLE → SELECTED` immediately (simple `update`, not inside a transaction — see §19).
   - NOBAR_COMMUNITY: `EventTable.bookedSeats` incremented inside a `$transaction` (re-checks capacity server-side to avoid oversell); status flips to `BOOKED` only once the table is full, otherwise stays `AVAILABLE` for other customers to pick different seats.
   - `Reservation` (`status: PENDING`, `expiredAt: now + 15min`) + `OrderItem`(s) created.
   - Midtrans Snap token requested and returned.
6. Client opens the Midtrans Snap popup. On success/pending → redirect to `/book/success?order_id=...`. On failure → alert + reload.
7. **Midtrans webhook** (`/api/midtrans/webhook`) is the only thing that finalizes the reservation:
   - `capture`(accept)/`settlement` → `Reservation.status = SUCCESS`, table → `PAID` (or seats confirmed, no table change needed for seat-based).
   - `cancel`/`deny`/`expire` → `Reservation.status = FAILED/EXPIRED`, table → `AVAILABLE` again (or seats released back for seat-based bookings).
   - `pending` → `Reservation.status = PENDING`, table → `SELECTED`.

**Known gap**: there is **no scheduled job** that sweeps `PENDING` reservations past their `expiredAt`. If Midtrans never calls the webhook (e.g. customer abandons before any Midtrans-side state change, or the webhook URL is unreachable), the table can remain `SELECTED` indefinitely instead of reverting to `AVAILABLE` after 15 minutes. See §19/§20.

## 13. Seat Layout Flow

- Background image: `public/layout-seat-v3.png` (swapped in from `layout-seat-v2.png` this session), rendered via `next/image` inside `SeatMap.tsx`, with a click-to-zoom modal.
- **Important**: table buttons are **not** positioned as clickable hotspots overlaid on top of the image at real (x, y) coordinates. They are rendered **below** the image, in a plain CSS grid, **grouped by `tableType`** (`Kategori VVIP`, `Kategori VIP`, …), sorted numerically by `tableCode`. The image is purely illustrative/reference — customers pick a table from the labeled grid, not by clicking a spot on the floor plan.
- Status colors: green = `AVAILABLE` (clickable), yellow = `SELECTED` (held, not clickable), red = `BOOKED`/`PAID`/`LOCKED` (not clickable), white/ring = currently selected by this customer.
- For `NOBAR_COMMUNITY` (`perSeat` prop), the label under each table code changes from `"{capacity} Pax"` to `"{capacity - bookedSeats}/{capacity} Seats Left"`, and a table stays clickable as long as any seats remain (not just when `status === AVAILABLE` with zero holds).
- All table/seat data (`capacity`, `status`, `bookedSeats`, `tableType`, `tableCode`) comes from the database (`EventTable`) — **not hardcoded**. The *generation* of the standard 48-table LUDO layout (which codes/capacities/types exist) **is** a hardcoded constant list in `lib/tableLayout.ts`, applied when admin clicks "Generate Tables" or when a match is auto-provisioned.

Status: **Existing**, but the "true floor-plan hotspot" interaction described in the roadmap template is **Need Development** — today it's a labeled grid, not click-on-image positioning.

## 14. Payment Gateway Flow

- Gateway: **Midtrans Snap**, sandbox/production switched by `MIDTRANS_IS_PRODUCTION` env var.
- Config file: `lib/midtrans.ts` — reads `MIDTRANS_SERVER_KEY`, `NEXT_PUBLIC_MIDTRANS_CLIENT_KEY`, computes the Snap API base URL, exposes `createSnapTransaction(payload)`.
- Snap JS SDK is loaded globally in `app/layout.tsx` via `<Script src=".../snap.js" data-client-key=... lazyOnload>`.
- **Create transaction**: `app/api/midtrans/checkout/route.ts` — see §12 for full sequence. `item_details` sent to Midtrans mirror the price breakdown exactly (package line, à-la-carte lines, a negative "Member Discount" line if applicable, an "Admin Fee (3%)" line) so the Midtrans-side receipt matches what the customer saw.
- **Callback/notification**: `app/api/midtrans/webhook/route.ts` — SHA-512 signature verification (`order_id + status_code + gross_amount + SERVER_KEY`) before trusting any payload field. This endpoint must be configured as the "Payment Notification URL" in the Midtrans dashboard for both sandbox and production.
- **Reservation status transitions**: `PENDING → SUCCESS | FAILED | EXPIRED` (webhook-driven only; the checkout route never sets a final status itself).
- **Table/seat status transitions**: tied 1:1 to reservation status transitions, branched by whole-table vs seat-based (§12).

Status: **Existing** and functioning (used throughout this session's testing). Midtrans is **not** "Need Development".

## 16. Transaction and XLSX Export

- Data storage: `Reservation` (+ `OrderItem` children) in MySQL — real transactional data, not mocked.
- Admin visibility: `/admin/transactions` (list all events with reservation counts) → `/admin/transactions/[eventId]` (full reservation list with status/table/package/customer).
- Filter by event/match ID: **yes** — every transaction view and the export endpoint are scoped to one `eventId` (query param). There is currently **no cross-event/global transaction list or date-range filter**.
- Export: `GET /api/admin/export?eventId=...` → `.xlsx` with **5 sheets**, already implemented:
  1. **Summary** — counts (total/success/pending/failed), revenue paid, table booked/available.
  2. **Detail Transaksi** — one row per reservation (customer, package, table, price, status, payment method, timestamps).
  3. **Rekap Per Package** — grouped by package name (order count, paid count, pending count, revenue).
  4. **Rekap Per Table** — one row per table (status, current customer if booked, transaction count).
  5. **Rekap Payment Status** — grouped by `ReservationStatus` (count + total nominal).

**Known limitation**: sheets 2–4 use `res.orderItems[0]` (only the *first* order item of a reservation). For reservations that include à-la-carte add-on lines (multiple `OrderItem`s per `Reservation`), the export currently only reflects the primary package/table line — additional à-la-carte items are invisible in the exported report even though they were paid for. See §19/§21.

## 22. AI Development Notes

- **Never hardcode event/match/package data on the frontend.** Everything in `app/page.tsx`'s `DEFAULT_*` arrays is an *emergency fallback only* (rendered when the DB query throws) — real content must always come from Prisma.
- **Don't restyle broadly.** This is a mature Tailwind design system (see the `ludo-*` custom color tokens in `tailwind.config.ts` and the repeated gradient/shadow patterns across public components) — match existing conventions rather than introducing new ones.
- **Booking must always be scoped by `bookingEventId`/`eventId`.** Every table, package, and reservation query in this codebase filters by the owning event — never query `EventTable`/`EventPackage` globally without that scope.
- **A reservation only becomes `SUCCESS` (and a table only becomes `PAID`) via the Midtrans webhook** — never set a final success status directly from the checkout route or from client code.
- **`PENDING` reservations must have an enforced timeout.** Currently only advisory (`expiredAt` column, no active sweep) — see §19/§20 priority 1 before shipping anything that depends on table availability being accurate in real time.
- **The Midtrans webhook must verify the SHA-512 signature before trusting any field** — this is already implemented; do not remove or weaken it.
- **XLSX export must read from the real database at request time** — it already does; if you extend it, keep it that way (no cached/precomputed report data).
- **Never expose `MIDTRANS_SERVER_KEY` to the client.** Only `NEXT_PUBLIC_MIDTRANS_CLIENT_KEY` is safe to bundle. Double-check any new code that touches Midtrans config.
- **`/book/[eventId]` must keep working for every dynamically-created event ID** — including ones auto-provisioned by `matchActions.ts`. Don't special-case specific IDs; branch on model fields (`eventType`, `isActive`, `packages.length`) instead.
- **Prefer `prisma db push` over `prisma migrate dev` on this project** until the migration history is reconciled (§9/§19) — the latter will try to reset the database.
- **The project root path contains spaces and Japanese Unicode characters.** Always quote paths fully in any script, CLI command, or CI config touching this repo; don't assume ASCII-only, slash-only paths.
- **`REGULER_MATCH` is a special "WhatsApp CTA only" template** — it deliberately has no tables/packages/payment flow. Auto-provisioned match events use `BIG_MATCH` instead specifically to avoid colliding with this rule. Keep that distinction in mind when adding new `EventTemplate` values.
